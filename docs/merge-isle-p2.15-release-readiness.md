## 发布候选版（RC）定义与硬性门槛

**当前处于开发中，不是 RC，也没有上线授权。** 应把「代码和 GitHub Actions 检查通过」与「真实设备及商业/内容验收通过」分开。

| 门禁 | 验收标准 | 当前观察 |
|---|---|---|
| A. 功能闭环 | 普通模式新手开局→生产→合成→交付→升级→补给→存档恢复→长期目标，手机触控无阻断 | P2 核心功能已过一轮 Windows 人工验收；新长期目标需复验 |
| B. 模式策略 | 首发明确采用普通模式单独试玩，或开放真正有内容且隔离存档的剧情模式；绝不把纯存档契约说成双模式可玩 | P2.12–P2.14 仅有剧情数据契约和内容包预检；没有真实剧情入口 |
| C. 剧情质量 | 若发布双模式版，必须验收首版剧情主支线、突发事件、关键角色及 DLC 延展接口；不锁死世界真相 | 待内容制作与人工审阅 |
| D. 存档 | V1/V2/V3 升级、断网、跨标签、冲突、损坏存档、浏览器重启、数据备份与恢复场景回归 | 已有代码测试；真实多端复验未闭环 |
| E. 云存档 | 如 RC 宣称支持跨设备云存档，必须独立测试 Supabase RLS、隔离 PostgreSQL 40 会话、Edge 网络与真实 iPhone 端到端，完成服务端模式协议迁移；不能只依赖 mock | **尚未完成，不允许宣称可用** |
| F. 设计与性能 | 原创图标/场景资源经过既定艺术验收并真实接入；iPhone Safari、微信 WebView、桌面小/大视口、长时间运行与弱网有数据 | 非美术研发分支仍显示占位图标，素材集成/实机待验收 |
| G. 安全与发布 | 最新提交全仓库回归、静态安全与部署隔离、完整 Git 历史密钥扫描通过；正式部署白名单检查；隐私和真实数据边界审查 | 每次单独验证；发布流程未授权 |
| H. 回滚 | 给出明确版本号、SHA、前后兼容存档策略、备份、回滚演练和部署后冒烟清单 | 待拟定 RC 工具与演练 |

### 推荐的两条交付线

1. **先做可验收的「普通模式离线体验版」**：不碰现有线上 Supabase，可独立完成 UI/美术/存档/设备验收后形成受控上线候选。必须明确「此版本仅本地存档，不支持跨设备同步」，不要包装为 V3 双模式云版。
2. **完整 V3 双模式版**：在不覆盖普通模式存档前提下实现剧情模式可玩的节点驱动、主线/支线/突发事件、独立故事包与存档；云存档在隔离验证完成后再决定是否进入首发清单。

任何版本的**正式合并、GitHub Pages/Cloudflare/Edge 部署、线上 Supabase SQL/迁移或生产数据接触都必须单独取得用户最终授权**。

## 实机复验
