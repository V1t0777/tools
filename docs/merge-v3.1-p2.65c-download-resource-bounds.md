# 《云屿百物铺》V3.1 · P2.65c 移动端下载资源上限与安全重试

**范围：普通模式独立研发分支。非美术工程，未发布。**

## 问题与目标

P2.65b 已将普通存档和异常重置备份统一到 Blob URL 下载协调器，并把正常链接存活期延长到 120 秒。真实 Safari/微信 WebView 可能暂停计时器，若连续多次点击导出，每个未释放的对象 URL 都可能保留一份最大约 2 MB 的备份，造成页面内存持续增长。既有实现仅在计时器正常运行时释放 URL，没有对无法清理时的连续下载进行上限约束。

本轮不改变存档格式、不添加自动导入或云端同步，而是封闭该资源安全边界。

## 相关实现（同一主题）

1. **下载内存上限**：`save-download.mjs` 在分配 Blob 前检查 UTF-16 输入长度，并在 Blob 分配后检查真实字节数，均不得超过 2,000,000。与既有 `save-export.mjs` 上限一致，防止其他调用方绕过导出器传入超大内容。
2. **待释放 URL 数量上限**：按 URL API 对象分别追踪最多 8 个待释放 Blob URL。达到上限时拒绝新请求，返回 `DOWNLOAD_LIMIT_REACHED`，不创建 Blob、不点击链接、不写入存档。
3. **安全清理与恢复**：正常计时器到期后释放并移除记录；计时器抛错、被暂停或异常同步执行时保留链接。下一次明确下载请求会尝试清理已超过 120 秒的记录。清理失败则保留记录并继续限制新请求，不谎称已释放。不能为了降低内存而提前回收正在由移动浏览器处理的 URL。
4. **页面提示与模式隔离**：普通存档及异常重置备份入口都明确提示下载过于频繁时稍后重试、不要清理或重置存档；两种导出都不修改普通模式、剧情模式或异常备份存储。

## 明确限制

- 下载成功回执仅代表浏览器接受了 anchor click 请求，**不等于文件已经落盘**；仍需真实 iPhone Safari、微信 WebView 的文件落盘验收。
- 若浏览器永远不执行清理计时器，且用户不再请求下载，最多 8 个 URL 仍会留存至页面销毁。此设计以有限内存占用换取不提前破坏尚在处理的移动端下载。
- URL API 对象与页面生命周期绑定，不跨标签或跨页面共享配额。
- 不修改 `main`、正式导航、部署白名单、云存档、线上 Supabase 或剧情研发分支；不发布，不合并 PR。
