# 《云屿百物铺》V3 · P2.27 启动迁移写入后读回校验（未发布）

## 本轮发现的具体风险

`loadLocal` 对 V1、V2 旧存档先创建版本化原始备份，再调用 `saveLocal` 写入 V3。此前 `saveLocal` 只根据 `setItem` 是否返回判定成功；若浏览器存储代理静默丢弃或截断写入，启动迁移仍会误报成功，并向 UI 返回并未真正持久化的 V3 原始字节基线。

## 最小修复

- 仅修改 `merge/storage.mjs` 中旧版升级写入成功后的分支：再次读取 `SAVE_KEY`，与序列化 V3 存档进行精确字节比较，匹配才报告迁移成功。
- 写入后读回不匹配或抛错时返回 `blocked:true`、`volatile:true`、`reason:'WRITE_VERIFY_FAILED'`；`raw` 保持升级前读取的原始文本，不谎称磁盘仍为旧版，也不自动重试/回滚。已经成功写入的版本化备份不被删除。
- 旧有 `WRITE_FAILED` 和 `BACKUP_UNAVAILABLE` 状态保持不变；确认重置与普通存档写入仍遵守 P2.26 的基线校验。
- 新增 `tests/merge-startup-migration-readback.test.mjs`：V1/V2 正常升级、静默丢弃写入、截断写入、写后读取异常、剧情存档隔离。

## 仍然存在的限制

这不是原子事务或跨标签 Web Locks 接线。写入后读取失败时，磁盘上的主存档可能已经改变，用户应保留备份并重新打开核对。旧版升级仍在同步启动阶段执行；跨标签竞争、移动端 Safari/微信 WebView、真实存储故障仍需实测。下轮优先研究迁移前后与页面初始 `persist()` 的冲突保护。

仅修改 Draft PR #58 的独立研发分支，不改 `main`，不合并、不发布、不改部署白名单、不运行线上 Supabase SQL/迁移、不接触生产数据库、不制作美术、不添加作弊后门。必须以本提交 HEAD 对应三项 CI 全部成功为工程完成标准。
