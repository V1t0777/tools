# P26：建筑支出与剧情前置的跨标签一致性检查

## 发现的问题
花园、港湾、门面按钮在点击时检查剧情前置条件，但 Web Locks 排队等待期间，其他标签可以重置或改变剧情对白存档。原工作台的独占锁只覆盖工作台存档键；排队完成后即使剧情前置已经失效，仍可能扣除工作台金币并建造建筑。

## 修复范围
- 新增纯读取守卫 `merge/story/building-commit-guard.mjs`：仅在花园、港湾、门面建筑状态变化时，验证提交前的**完整剧情存档原文**仍未变化，并重新验证对应章节前置。非建筑操作不依赖对白存档。
- 在工作台 `runStoryWriteWithLock` 回调内部、`writeStoryWorkshop` 之前执行守卫。前置变化、损坏、缺失或存储不可用时拒绝金币支出。旧的原文 CAS 与 Web Locks 均保留。
- 测试覆盖三座建筑、锁等待时对白重置、非关键对白更新、异常存档、普通模式隔离及非建筑操作。

## 局限
两份独立 localStorage 键不是原子事务；其他标签若不遵循锁协议，仍可能在极端并发时序下交错。该守卫是保守的二次核对，不是跨键事务。iPhone Safari / 微信 WebView / BFCache 仍需真机验收。
