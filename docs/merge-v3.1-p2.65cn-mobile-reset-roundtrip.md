## 同 SHA 首次 CI 失败的诊断与修正

首次 GitHub Actions `Security checks #41085723311` 的 Node 回归为 1229/1230，失败于既有 `merge-browser-real.test.mjs` 的“其他标签采纳重置后合法写入”断言。故障快照显示 B 标签的原始存档已更新为 revision 1、体力 119，页面体力也为 119/120，但保存状态显示“已保存于此浏览器”，而原测试只接受“已同步”。

因此只调整该项 UI 文字判定：允许“已同步”或“已保存于此浏览器”，同时**保留**页面体力校验及后续原始存档逐字节等于 A 标签写入值的强断言。不增加等待时间、不自动重试、不放宽存档一致性。此处是测试判定对合法状态文案的兼容，不代表运行时缺陷已被排除；以修正后新 SHA 的三项 CI 为准。

### 第二次 CI 失败：导入互锁的两条安全拒绝路径

新 SHA `bac73db4` 的首次回归仍为 1229/1230，故障快照显示在 A 标签持有真实 Web Lock 期间，B 标签已拒绝导入并显示“正在安全保存或其他标签页占用存档，请稍后重试”；旧断言仅接受“其他标签正在保存”。代码中前者来自 `UI_TRANSACTION_BUSY` / `SAVE_LOCK_BUSY` 的页面级互锁，后者来自导入流程的 `LOCK_BUSY`。二者均是安全拒绝，不表示恢复成功。

测试现接受两种明确的安全拒绝提示，但仍要求确实发生一次用户确认，且存档、恢复备份、剧情存档原始字节不变；不会把任意提示当作通过，不重试失败导入。下一步仍需调查 CI 中页面级忙状态的触发时序，并以新 SHA 完整回归为准。
