# P18 · 剧情对白与经营工作台的跨标签前置条件刷新（Draft）

## 用户可见缺口
剧情对白页根据剧情工作台的订单与建筑状态显示“待完成经营目标”；经营工作台根据对白页的已读进度启用花园、港湾、门面修复按钮。此前只监听自身存档键：另一标签更新**另一种剧情存档**时，当前页面会继续显示过期的解锁状态，直到用户切页、刷新或尝试点击。点击时已有二次核对，但提示可能滞后。

## 变更
- 在 `storage-event-guard.mjs` 增加纯函数 `shouldRefreshStoryDependencyEvent`，只对另一剧情专用存档键的同一 localStorage 区域变化返回 true。其他区域、普通模式键、无效键和 `clear()` 都不当作普通刷新。
- 剧情对白页收到工作台键变化后，关闭已打开的对白框，清除尚未确认的选项并重新计算每幕经营前置条件；不覆盖剧情已读进度。
- 经营工作台收到对白键变化后，重新计算建筑按钮启用条件；不修改棋盘、金币或物品。
- 自身存档键变化及 `clear()` 仍沿用 P16 的只读阻断。普通模式键变化完全忽略。

## 测试
`tests/merge-story-cross-mode-events-p18.test.mjs` 包含双向刷新判定、无关存储隔离、`clear()` 保持阻断、真实引擎订单解锁与静态 UI 合约。只代表 Node 模拟/静态测试，不是 iPhone Safari/微信 WebView 真机。

## Web Locks 评估与后续
当前 P17 第二次写前核对仍非原子事务。Web Locks 只有在所有相关写入路径都使用同一命名锁时才能序列化合作方写入；不支持该 API 的浏览器或 WebView 必须有明确的失败封闭/降级策略，不能默默把有锁路径当成已全局安全。鉴于需要把同步 writer 与 UI 保存调用改为异步并处理关闭页面/锁等待，P18 不贸然引入锁机制。后续需设计可测试的完整改造，并在真实 iPhone/微信环境验证支持情况。
