# 《云屿百物铺》V3.1 · P2.65a 动态按钮失效代际门禁（仅 Draft 研发分支）

## 问题定位

P2.64f 已将普通模式 HTML 入口切换到 `main-locked.mjs`，四类存档写入统一进入 Web Locks 事务。此前 P2.64e 的存档预检可以拒绝**第一个发现跨标签更新的输入事件**，但还有一个真实浏览器事件队列边界：其他标签的存档已经被只读采用，页面已重建订单/仓库/工坊/补给 DOM，此时旧节点上已排队的 `click` 监听器仍可能被执行。

由于旧节点回调捕获了订单 ID、仓库槽位、工坊 ID、补给类型，单靠存档字节 CAS 已无法辨别“这是用户对旧 UI 的操作”还是“对新状态的有效操作”。即使引擎重新验证价格和数量，旧按钮仍可能对新状态执行用户未确认的购买、交付或升级。

## 本轮一组闭环变更

1. **统一代际令牌**：`main-locked.mjs` 的完整 `render()` 每次递增 `renderGeneration`；`guardRenderedAction` 在创建动态按钮时捕获当前代际。旧节点事件到达时只显示“界面已更新”提示，不进入 `commit()`，不请求 Web Lock，也不读取或写入存档。
2. **订单/仓库/建设与工坊**：订单交付按钮、仓库取出按钮及 `actionButton` 生成的工坊升级/建筑建设按钮统一通过代际门禁。静态按钮仍使用已有 `revalidateResumedSave()` 和事务门禁。
3. **补给使用/限量商店**：补给消耗和金币兑换按钮统一采用代际门禁；补给工坊选择仍在真正点击时捕获，避免等待异步 Web Lock 期间重定向目标。时钟未改变存档时只刷新资源/冷却控件，不增加完整渲染代际。
4. **活跃 HTML 入口 DOM 回归**：在 `tests/merge-locked-page-dom.test.mjs` 增加 5 项测试：跨标签后的旧订单、BFCache 后的旧仓库、旧补给消耗、旧工坊升级，以及本标签仅选择棋盘触发重渲染后的旧商店按钮。每项验证旧回调零写入，同时验证最新页面上的新按钮仍可完成合法事务。

## 安全不变量与测试边界

- 代际门禁是 **UI 语义防重放**，不代替 Web Locks、原始字节比对、可信读回和引擎规则。代际检查与 `commit()` 之间仍需原有跨标签预检，锁内仍需精确原始存档检查。
- `render()` 执行时才更新代际；仅每秒无变化的资源/冷却刷新不会反复让按钮失效。旧事件不允许“自动重试”或重新解释为新状态上的点击。
- 不修改存档 schema、经济参数、模式命名空间、云端代码、美术、正式导航、部署白名单或线上数据库。
- Node DOM 模拟可证明事件处理器和内存存档边界，**不等于真实浏览器的事件队列时序、iPhone Safari、微信 WebView 或 BFCache 实机验收**。仍需双标签和移动端实机测试。
